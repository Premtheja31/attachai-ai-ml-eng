# DESIGN_NOTES.md

## Part 2 — the fix, and the multi-turn session flow issue

**What I fixed as #1 (introductions endpoint).** The root cause was that `generate_reason` authenticated the caller but never *authorized* them, and exposed raw attribute rows with no policy. The fix addresses the whole class, not one example: both target members are resolved (404 if missing), both must belong to the caller's club (403 otherwise), and the attribute query itself excludes `restricted == True` and anything below `settings.intro_confidence_threshold` (env-configurable, default 0.6) — so no caller, path, or prompt change can reintroduce the leak. When nothing qualifies, the endpoint says "insufficient basis for an introduction" instead of inventing one.

**The session-flow issue (fixed as the "one more").** In `advance_turn`'s `affirm` branch, `payment_mock_client.charge()` ran before any row was persisted — if the process died between the charge and `db.commit()` (reproducible via `simulate_crash`), the DB had no record a charge happened, the session was still `awaiting_confirmation`, and the client's natural retry charged the card again. The fix inverts the order around the charge: a `Booking` plus a `PaymentAttempt(status="pending", idempotency_key=f"session-{session.id}-attempt-{n}")` are committed *before* the provider call, the charge carries that idempotency key, and the provider (like Stripe) replays the original outcome for a repeated key instead of charging again. On retry, `advance_turn` finds the pending attempt and re-submits the same key; a prior succeeded attempt short-circuits to "confirmed" without any provider call; and session/booking state now follows the charge result, so a failed charge no longer reports a confirmed session.

**Seed script wipe-list.** `scripts/seed.py` could not actually re-run once the session flow had been used — its delete loop omitted `ConversationSession`, so `DELETE FROM bookings` hit the `conversation_sessions.booking_id` FK. Added `ConversationSession` to the wipe list; the seeded data itself is unchanged.

## Part 3 — extraction pipeline

**Idempotency key.** A message counts as already processed when this query, exactly as it appears in `ExtractionService._already_processed`, finds a row:

```python
self.db.query(MemberAttribute).filter(MemberAttribute.source_message_id == message.id).first() is not None
```

i.e. the key is **`member_attributes.source_message_id`** — the existing FK linking an attribute to the message it was extracted from. No new column was needed. Idempotency therefore costs one indexed-lookup-shaped query per message and the re-run makes zero LLM calls for processed messages (asserted in tests via `fake.calls`). One documented caveat: a message that legitimately yields *zero* attributes leaves no row behind, so a re-run re-extracts it — idempotent in effect (zero rows → zero duplicates, every time) but not in API-call count. Accepting that beats the alternatives: a sentinel attribute row would pollute the shared attributes table, and a processed-flag column is a schema change this assignment forbids. If I owned the schema I would raise adding a nullable `processed_at` timestamp on `conversation_messages` with whoever owns it, not add it unilaterally.

**Retry strategy.** Lives in one place, `OpenAILLMClient.extract_attributes`: up to `llm_max_attempts` (default 3, configurable) attempts with exponential backoff plus jitter (1s/2s/4s-class waits), retrying only transient failures — 429 rate limits, 5xx, timeouts, connection errors (`_is_transient`). Non-transient errors (401 bad key, 400 malformed request) raise immediately: retrying those wastes time and hides bugs. The OpenAI SDK's own silent retries are deliberately disabled (`max_retries=0`) so the retry strategy is visible, testable, and singular — otherwise 3 of ours × 3 of theirs = 9 hidden requests. When a message exhausts its retries, `ExtractionService._process_one` catches the exception, records `{"status": "failed", "error": ...}` for that message only, and the loop continues — one message's permanent failure never fails the batch (test: `TestExtractionFailureIsolation`; batch-of-3 with the middle one failing yields processed/failed/processed with the successes committed). Each message's attributes are committed individually, so a crash mid-batch loses at most the in-flight message and a re-run skips the completed ones via idempotency.

**How a restricted attribute is kept out of matching.** Write side: restricted extractions are stored with `restricted=True` — flagged, never silently dropped. Read side — the actual check — is in `build_member_profile_text` (`app/services/matching_service.py`):

```python
MemberAttribute.restricted.is_(False)
```

applied unconditionally in the attribute query (plus a configurable confidence floor, `matching_confidence_threshold`, default 0.0). This function is the *single* source of the text that becomes `profile_embedding`: `rank_candidates` builds the query vector from it, and `refresh_member_embedding` (now called by `ExtractionService` after each batch for every member who gained attributes) builds the stored candidate vectors from it. Because extraction and matching share the `member_attributes` table, enforcement had to live at the read boundary — this one choke point means no caller of the matching pipeline can see restricted text, regardless of how the attribute got written. The end-to-end test (`TestRestrictedEnforcement`) extracts a restricted + unrestricted pair through the real endpoint and asserts the profile text contains only the unrestricted one and that the embedding was refreshed.

**Why the threshold is 0.75.** Scoring: a record passes only if all three checks pass (kind, keyword, restricted); overall = passed/4; the run exits non-zero below threshold **or on any restricted mismatch, regardless of score** — privacy misclassification has zero tolerance. Measured baseline: 5 consecutive eval runs, all 4/4, zero restricted violations. The threshold is set at 0.75 anyway because the eval is a regression tripwire, not a target: with n=4 and a nondeterministic system under test (temperature 0 reduces but does not eliminate output variance), a 1.0 bar converts a single borderline kind-judgment wobble (e.g. record 2 is defensibly offer *or* context) into a false CI failure, while any genuine regression — broken prompt, broken parsing, inverted restricted logic — takes out two or more records and fails 0.75 just the same. Lenient where human annotators would disagree; zero-tolerance where the business risk lives.

## Closing question — what I deliberately did not do, and what I'd build next

Deliberately skipped, in priority order of what I'd build with one more day:

1. **Async job execution for extraction.** The endpoint is synchronous-sequential by choice: job state needs persistence ("no new tables" rules that out here), concurrent fan-out to OpenAI causes the very 429s the retry strategy then fights (thundering herd), and FastAPI runs sync endpoints in a threadpool so the server isn't blocked — only the caller waits. At real WhatsApp-ingest scale that tradeoff flips: day one I'd make `POST /extract-attributes` return `202` with a job id backed by a jobs table and a worker pulling from a queue, with per-message status transitions replacing the in-response statuses.
2. **Fixing the remaining reviewed-but-unfixed payment bugs** — client-controlled `amount_cents` in `confirm-payment` (REVIEW.md #3) and its missing idempotency/status guard (#4). I fixed the two highest-impact issues end-to-end rather than five issues shallowly; #3 is a three-line fix but deserved its own before/after trace I didn't have time to record.
3. **A bigger golden set.** Four records can't measure a 4-kind × restricted classifier meaningfully — the 0.75-vs-1.0 threshold debate exists *because* n=4. I'd expand to ~50 labeled messages (mining the real conversation history), add per-kind precision/recall, and track scores across prompt versions.
4. **Confidence-threshold tuning with data.** Both thresholds (`intro_confidence_threshold=0.6`, `matching_confidence_threshold=0.0`) are defensible guesses. With match-acceptance or intro-acceptance data I'd tune them against observed outcomes instead.
